# Design: Template-owned potion supplies

Generated by office-hours on 2026-08-31  
Status: DRAFT  
Mode: Builder

## Problem statement

Potion supplies are currently stored in `potion-storages.yml` as map-relative
coordinates. A round is rejected when an enabled map's copied template no
longer contains a chest at one of those saved coordinates. This makes an old
implementation detail veto later map edits. The operator wants calibration to
be the map-authoring workflow: edit the map freely, save it, and have the
saved template define the live round without manually maintaining a separate
coordinate registry.

## What makes this cool

A calibrated map is a self-contained artifact. Copying its clean template
copies its team-owned supplies too. Moving or deleting a supply chest during
calibration changes the next round naturally; it cannot fail a rotation
because an external file remembered an old location.

## Premises

1. A successful calibration save is authoritative for all physical map layout.
2. Supply ownership and refill contents must remain explicit. An ordinary
   player-built chest must never become an infinite team supply by accident.
3. Deleting a claimed supply chest removes that supply from future copies. It
   warns operators but never rejects an otherwise usable map.
4. Basic map safety checks may remain as guardrails, but manual calibration is
   the primary authoring process.

## Chosen approach: supply identity stored in the map template

Each claimed double chest owns its supply definition in its two saved chest
block entities. The plugin writes a shared supply UUID, owning team, and
refill-item definition into the Persistent Data Container of both chest halves
while a calibration copy is open. The calibration promotion path already saves
the world and promotes that exact copy into the clean template, so this data
travels with every future generated round.

At round preparation, the plugin scans the loaded map for valid, paired tagged
double chests and creates the runtime supply contexts from what it finds. No
active round reads a map-relative supply-coordinate registry. A missing,
deleted, malformed, or orphaned tag is reported as a map warning and ignored
for that supply; it is not a reason to reject the map or fall back to another
one.

## Operator workflow

1. Start `/siege admin map calibrate <map-id>`.
2. Build, move, or remove ordinary blocks and chests freely.
3. Point at a double chest and claim it with a calibration-only command such
   as `/siege admin supply claim <red|blue>`. Its current uniform potion/food
   contents become the refill template and its tag is saved into both halves.
4. Point at a claimed chest and run `/siege admin supply unclaim` to turn it
   back into an ordinary chest.
5. Finish calibration. The promoted template contains the final blocks and
   supply tags. The next rotation discovers supplies from that template.

No coordinate copying, external registry editing, or re-registration after a
move is needed.

## Runtime rules

- A supply works only for a battlefield fighter on its tagged team; existing
  Towny/team permission enforcement remains.
- A tag is valid only when both halves of the same double chest carry matching
  supply ID, map-independent metadata, and contents definition.
- A tagged pair outside current arena bounds is ignored and warned about. It
  cannot grant supplies to players outside the battlefield.
- A removed chest has no tag to discover, so it is absent from the round.
- Duplicate, half-paired, or malformed tags are ignored with a concise
  operator warning. They do not block map activation.
- Runtime labels remain temporary visual helpers. They are recreated from the
  discovered tagged chests and are not the durable identity.

## Migration

The first release retains `potion-storages.yml` only as a migration source.
For each legacy record, staff opens the relevant map in calibration and claims
the intended chest once. After that map has at least one saved template using
the new tags, the legacy entries for that map are ignored. A later release may
remove the file and old coordinate model after all enabled maps are migrated.

The Iron Mountain failure is repaired by opening Iron Mountain calibration,
placing or selecting the intended chest, claiming it for its team, and saving
the template. Its stale record at `-17305,93,-7727/-7726` then has no authority
over future rounds.

## Approaches considered

### A. Do not block rotation on missing supplies

Smallest change. Keep the external coordinate registry but make absent chests
warnings. This unblocks rotation but leaves every moved chest as manual
registry maintenance and can silently remove a team's supplies.

### B. Reconcile external coordinates when calibration finishes

Refresh the registry from each calibration copy. Better than A, but supply
identity remains split between the template and a separate coordinate file.
The server is still capable of disagreeing with the map it just saved.

### C. Template-owned supply tags (chosen)

Put the source of truth where the physical object lives. This removes
coordinate drift and makes map copies portable while preserving explicit team
ownership and refill data.

## Open questions

1. Should malformed/half-paired tags only log a warning, or should calibration
   finish refuse to save until the admin fixes them? Recommended: reject only
   the affected claim operation; warn and ignore pre-existing malformed tags
   during rotation.
2. Should the claim command overwrite an existing supply tag only with an
   explicit `--replace` confirmation? Recommended: yes, to avoid accidentally
   changing a team's refill definition.
3. Should claimed chest contents be cleared and immediately refilled after
   claim, as they are today? Recommended: yes, so calibration visibly confirms
   the chosen refill template.

## Success criteria

- Moving or deleting a claimed chest in calibration never prevents the map from
  being saved or rotated.
- A generated live copy discovers exactly the supplies tagged in its promoted
  template.
- An unclaimed chest never becomes a supply.
- Team and battlefield permission rules remain unchanged.
- Iron Mountain can be recalibrated and rotated without any external
  coordinate-file edit.

## What I noticed

The important requirement is not merely "make the validation less strict." It
is that saving through calibration must make the server conform to the map you
edited. Template-owned tags make that true without treating every chest as a
supply or weakening team permissions.
