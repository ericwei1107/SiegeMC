# Design: Clean-Copy Map Rotation

Generated by office-hours on 2026-08-28  
Status: DRAFT  
Mode: Builder

## Problem Statement

SiegePlugin is currently bound to one persistent `siegeworld` and an eternal score record. The community server needs finite rounds: a team reaches a configurable score limit, players see a winner announcement and lobby countdown, a newly revealed map begins at 0–0, and map damage never leaks into the next round.

## What Makes This Cool

The round ending is a ceremony rather than a loading failure: the winner is visible, players regroup in the lobby, the next map is revealed during a countdown, and everyone enters a clean battlefield together. The original map templates stay pristine forever.

## Premises

1. Map templates are immutable source worlds. A round runs only in a generated active copy, which is unloaded without saving and deleted after use.
2. Terrain from Sieges is reused, but every map is given a SiegePlugin manifest for Red/Blue spawns, capture banner, boundary, lobby handoff, and optional potion supplies. SiegePlugin retains its own kits and banner-control game mode.
3. Score-limit rotation is transactional. No score reset/new match occurs until a target map has copied, loaded, and validated successfully.
4. A failed rotation keeps the completed winner/score archive exactly once and leaves players safely in lobby recovery; it never reruns or double-awards the old match.
5. Map voting, kit voting, and kill/damage/banner/overall MVP presentation are later features and are not implementation scope now.
6. The map owner has authorized reuse. Keep provenance/attribution documentation with the imported assets before publishing the open-source distribution.

## Reference: How Sieges Rotates

Sieges uses `FileMapLoader`: it copies a configured source world folder into `<template>_active_<number>`, excluding `session.lock` and `uid.dat`; loads that folder through Bukkit; disables autosave and applies match game rules; and later unloads without saving then recursively deletes only the active folder. `GameManager` shuffles its map queue, preloads the next map, delays the new game, and unloads the prior active copy after players leave.

SiegePlugin borrows the clean-copy idea, not the legacy implementation details: it will not kick players, recurse-delete broadly, or let score reset race a map load.

## Approaches Considered

### A. Reuse one live arena world

- Effort: S; Risk: High
- Reuse the existing snapshot system to import/reset maps into `siegeworld`.
- Rejected: this is not truly clean-copy rotation and exposes the active round to failed imports.

### B. SiegePlugin transaction with a Multiverse adapter

- Effort: L; Risk: Medium
- SiegePlugin controls the state machine while Multiverse loads/unloads copied worlds.
- Rejected: Multiverse adds a second lifecycle owner without solving transactional score/player safety.

### C. SiegePlugin-owned native Bukkit/Paper clean-copy loader — selected

- Effort: M; Risk: Low
- Copy template folders asynchronously, create/unload worlds through Bukkit/Paper on the main thread, and delete only generated active copies.
- Selected: closest to the proven Sieges workflow with one clear owner for match state.

## Recommended Approach

Approach C. It keeps the plugin responsible for the only decisions that matter to players—when a round is complete, where they go, when the next round begins, and when its scores become active—while using the proven template-copy lifecycle from Sieges.

## Rotation State Machine

`ACTIVE → COMPLETING → LOBBY_CEREMONY → PREPARING_COPY → REVEAL → ACTIVATING → ACTIVE`

1. **ACTIVE:** durable scoring runs; a score-limit detector observes the post-write match score.
2. **COMPLETING:** one idempotent transition token freezes scoring/capture rewards, closes the winner record, and cancels capture sessions.
3. **LOBBY_CEREMONY:** participants move through the existing safe lobby transition; announce winning team and countdown.
4. **PREPARING_COPY:** select a validated non-repeating template, copy it to a unique generated folder, load/configure the runtime world, and validate the manifest against it.
5. **REVEAL:** announce map name only after preparation succeeds.
6. **ACTIVATING:** replace all static-world bindings, spawn teams, create the zero-score match, and reopen scoring.
7. **Cleanup:** after no player remains, unload the prior active world without saving and delete only that generated folder.

If preparation fails, enter a visible lobby-recovery state; retain the completed match and offer a validated fallback/retry path. Do not create the new match or reopen scoring.

## Required Refactors

- Replace the eternal `MatchDefinition.eternalForWorld(...)` model with a distinct match record per activated round.
- Make `CaptureService`, team spawns, arena boundary/reset, minecart cleanup/protection, sidebar world/map context, and potion-supply location resolution bindable to an active map rather than boot-time `siegeworld` config.
- Replace scheduled in-place arena reset as the normal round boundary. It remains useful only as a recovery/admin tool if retained.
- Add a map manifest/validator and a runtime world loader abstraction; map manifest must be validated before a template enters rotation.
- Trigger rollover only after the winning score has persisted; ensure repeated score callbacks cannot create two rotations.
