# Design: Global Personal Siege Kit Editor

Generated by office-hours on 2026-08-28  
Status: IMPLEMENTED IN WORKING TREE
Mode: Builder

## Problem Statement

Players need a quick way to personalize the replaceable supplies in the default Siege kit without changing combat essentials or creating a different loadout for every map. The previous editor was unreliable—menu clicks did not consistently produce equipped items—and its workflow did not match the intended two-choice `/siege kit` experience.

## What Makes This Cool

The feature removes friction between fights. A player chooses a few preferred supplies once, saves them globally, and can equip the resulting kit from one obvious menu on every map. It feels personal without becoming an unrestricted creative inventory or an admin chore.

## Premises

1. Every player has at most one personalized Siege kit shared by all maps.
2. The configured default kit remains the authoritative fallback for a player with no saved customization or an invalid saved record.
3. Armor, the primary sword, and offhand are immutable essentials. They are never presented as editable choices and are always rebuilt from the current default kit.
4. Players do not move arbitrary inventory items into the editor. Every replacement comes from a staff-configured list of legal choices.
5. Editing happens in a temporary session. Back and Cancel preserve the draft while navigating; Cancel Without Saving, closing the editor, disconnecting, or dying discards it.
6. **Save & Equip** validates and persists the personalized kit, closes the GUI, and immediately equips it. A failed save keeps the previous durable kit and reports the failure instead of equipping unpersisted state.
7. Shop purchases and other temporary inventory contents can never become part of a saved kit.

## Reference: What Sieges Does

Sieges exposes `/kits set <map|allmaps>` and saves a snapshot of the player's current inventory. Its `allmaps` record acts as a fallback, and it filters paid shop items before persistence. Kits are stored through Hibernate using serialized `ItemStack` data and restored after kit lookup.

The useful idea is player-owned persistent customization. The implementation should not be transplanted:

- Per-map records conflict with SiegePlugin's global-kit requirement.
- Capturing the current inventory is unnecessarily risky for duplication and temporary-item persistence.
- Raw serialized `ItemStack` data is fragile across Minecraft versions.
- The save path appears to save the newly created kit repeatedly while iterating existing kits.
- Its cache, asynchronous lookup, and main-thread inventory application do not provide the lifecycle guarantees already available in SiegePlugin.

## Implemented Validation Foundation

Reuse the safety model already present in SiegePlugin:

- `KitSnapshot` supplies the trusted, configuration-backed default kit.
- `KitItemSpec` provides a normalized representation of a permitted item rather than trusting arbitrary player inventory state.
- `KitSlotKind` distinguishes storage slots from armor and offhand slots.
- `KitChoiceCatalog` parses staff-configured replacement groups, rejects locked slots, and disables malformed groups independently.
- `KitLoadoutAssembler` rebuilds the complete kit from the current snapshot and normalized choice IDs.
- `KitValidator` requires the assembled specifications to exactly match that trusted reconstruction.
- `KitSelectionDao` persists one normalized global selection per player in SQLite. The legacy serialized table remains untouched but is no longer read.
- `KitEditSessionStore` provides temporary per-player editing state.

The old hard-coded allowance palette and raw serialized personal-loadout path were removed so save, load, lifecycle equip, and direct equip all use one reconstruction path.

## Approaches Considered

### A. Minimal slot editor

- Effort: S; Risk: Low
- Let players rearrange the editable items already present in the default kit.
- Rejected: it does not provide the requested replacement choices and offers little meaningful personalization.

### B. Configured replacement menus — selected

- Effort: M; Risk: Low–Medium
- Each editable supply slot opens a staff-configured menu of legal replacements. The plugin owns the draft, reconstructs the finished kit, validates it, saves it, and equips it.
- Selected: it matches the intended experience while staying narrow enough to make correctness and testing practical.

### C. General-purpose loadout builder

- Effort: L; Risk: Medium
- Build dynamic categories, dependencies, budgets, pagination, and hooks for future kit/map voting.
- Rejected for 1.1: it adds systems that regular players do not need yet and couples this editor to undecided voting infrastructure.

## Selected Player Flow

### `/siege kit` launcher

The command opens a small menu containing two actions:

1. **Equip My Siege Kit** — equips the player's valid saved kit, or the current default kit if none exists.
2. **Customize My Siege Kit** — opens a draft initialized from the saved personalized kit, or from the default kit for a first-time user. Lore should say that the customization applies on every map.

Use “My Siege Kit” rather than “Edit Default Siege Kit”; the player is not modifying the server-wide default.

### Editor

- Show only customizable supply slots or tiles. Locked armor, sword, and offhand are omitted rather than shown as misleading clickable items.
- Clicking an editable item opens its configured replacement list.
- Clicking a replacement updates only the server-side draft and returns to the editor.
- A child menu always includes Back and Cancel. Back returns without changing the current selection; Cancel Without Saving ends the entire session.
- The main editor includes **Save & Equip**, **Reset Draft to Default**, and **Cancel Without Saving**.
- Reset changes the draft to the current default choices but does not persist until Save & Equip is selected.

### Save & Equip

1. Reject additional clicks and show a short saving state.
2. Rebuild mutable slots exclusively from their selected configured `KitItemSpec` values.
3. Merge immutable armor, sword, offhand, and all non-customizable slots from the latest `KitSnapshot`.
4. Run `KitValidator` against the complete reconstructed loadout.
5. Persist stable choice IDs through `KitSelectionDao` off the main server thread.
6. On successful persistence, return to the main thread, close the GUI, and equip the exact validated loadout immediately.
7. On failure, retain the previous saved kit, keep the player out of a partially applied state, and display an actionable error.

## GUI and Session State Machine

`CLOSED → LAUNCHER → EDITOR ↔ CHOICE → SAVING → CLOSED`

- Cancel every click and drag involving a plugin-owned inventory before interpreting an action. Never allow Bukkit's default inventory movement to implement a menu choice.
- Interpret actions only from known top-inventory slots and plugin-owned item/action identifiers, not display names alone.
- Give each edit session a generation token. Delayed callbacks from an earlier menu or save must not mutate a newer session.
- Mark intentional menu transitions so the `InventoryCloseEvent` fired while moving between editor and choice menus does not discard the session.
- Close, quit, death, plugin disable, or an unexpected world transition invalidates the session and any pending UI callback.
- Perform Bukkit inventory and GUI operations on the main thread; perform database work asynchronously.

This explicit transition handling is the primary defense against the earlier “clicked but nothing equipped” class of bugs.

## Configuration Model

Keep replacement options administrator-controlled and readable in configuration. Each customizable entry should define:

- A stable choice-group key.
- The mutable kit slot or logical supply tile it controls.
- A display icon/name for the editor.
- An ordered list of permitted `KitItemSpec` choices.
- An optional default choice inherited from the authoritative kit snapshot.

Configuration must be validated at startup/reload. Disable only invalid groups and report precise paths; never expose a partially parsed choice. A choice group may target storage slots only and must not overlap locked essential slots.

## Validation and Recovery Rules

- Validate on configuration load, editor save, database load, and immediately before equip.
- If a saved choice no longer exists after an admin configuration change, substitute that slot's current default and report/migrate the stale record rather than rejecting the player's whole kit.
- If the complete saved loadout is unsafe or corrupt, quarantine/fail closed to the default kit.
- Equipping must clear/replace the intended Siege kit slots through the existing controlled kit application path; it must not append items to whatever the player currently carries.
- Repeated Save & Equip clicks are idempotent while a save is in flight.
- A server shutdown during save leaves either the prior durable kit or the complete new kit—never a partially persisted record.

## Test Strategy

1. Unit-test configured choice parsing, locked-slot rejection, reconstruction, stale-choice fallback, and full-loadout validation.
2. Unit-test the session state machine, including editor/choice close-event transitions, cancel, reset, repeated save clicks, and stale generation tokens.
3. Test DAO success/failure behavior and verify that equipment occurs only after successful persistence.
4. Stage on a live Paper server: click every menu route, close each GUI unexpectedly, disconnect during editing/saving, die while editing, reload configuration, and confirm that armor/sword/offhand and shop purchases can never be saved.
5. Verify that the saved global kit equips identically after changing maps.

## Explicitly Deferred

- Per-map personalized kits.
- Kit voting, map voting, and loadout budgets/cost systems.
- Player-created arbitrary replacement choices.
- Armor, sword, or offhand customization.

## Implementation Status

The launcher, editor, choice menu, saving state, normalized persistence, stale-choice healing, grant-only cooldown, and trusted lifecycle equip path are implemented. The packaged configuration ships with `kit.editor.slots: {}` and a commented schema rather than balance presets. Automated coverage is in place; the remaining release gate is the live Paper interaction matrix described above.

## What I Noticed

The goal is not a deep build-crafting system. It is a reliable convenience feature for experienced players who want less friction between fights. You pushed away from both per-map customization and unrestricted inventory capture, while insisting that the final click actually gives the player the kit. That makes the right product boundary unusually clear: a small, global, curated choice system with a trustworthy Save & Equip finish.
